# Decisions

## D-001. `_workspace` 파일 이름 충돌 → AGENTS.md 기준 사용

- 배경: AGENTS.md 는 `00_input.md`, `03_task_board.md`, `04_file_map.md`, `05_edit_plan.md`, `06_implementation_spec.md`, `07_validation.md`, `08_error_log.md`, `99_decisions.md` 를 지정한다.
  SKILL.md §4 는 `01_domain_analysis.md`, `02_selected_cores.md`, `03_work_plan.md`, `05_implementation_log.md`, `06_validation_report.md`, `07_change_history.md`, `99_pending_items.md` 를 지정한다. 두 목록이 다르다.
- 결정: **AGENTS.md 목록을 기준으로 사용**한다. SKILL.md 의 도메인 분석/코어 선택 문서는 `01_domain_analysis.md`, `02_selected_cores.md` 로 **보충**만 한다.
- 근거: SKILL.md §2 규칙 우선순위(사용자 요청 > AGENTS.md > SKILL.md). SKILL.md §4 도 "기존 프로젝트에 다른 `_workspace` 파일 이름이 이미 사용되고 있다면 강제로 변경하지 않는다"고 명시.
- 영향: `_workspace` 파일명은 AGENTS.md 기준. 작업 계획은 `05_edit_plan.md`, 구현 명세는 `06_implementation_spec.md`, 검증은 `07_validation.md`, 에러는 `08_error_log.md` 를 사용한다.

## D-002. SQLite 드라이버: `node:sqlite` 사용 (better-sqlite3 미사용)

- 배경: Electron 에서 SQLite 를 쓰려면 (a) `better-sqlite3` + electron-rebuild(네이티브 빌드 필요, Electron 44 ABI 프리빌드 미보장), (b) `sql.js`(WASM, 파일 저장 수동), (c) Electron 내장 Node 의 `node:sqlite` 중 선택해야 한다.
- 결정: **(c) `node:sqlite` `DatabaseSync`** 사용.
- 근거: 로컬 Node v22.15.1 에서 한글 저장/조회 포함 정상 동작을 실측했다. 네이티브 컴파일·프리빌드 의존이 없어 설치 실패 위험이 가장 낮다.
- 검증 필요: Electron 44 런타임에서의 가용성 → `scripts/smoke.js` 에서 확인한다.
- 영향: `main/db/index.js` 는 `node:sqlite` 만 사용한다. 사용 불가 시 명확한 오류를 띄우고 종료한다.

## D-003. 렌더러: 번들러 없이 Vanilla ESM + 커스텀 `app://` 프로토콜

- 배경: React+Vite 는 빌드 단계가 필요하고, `file://` 에서는 ESM 스크립트가 CORS 로 차단된다.
- 결정: **번들러 없이 Vanilla ESM** 을 쓰고, 메인에서 `protocol.handle('app', ...)` 로 `renderer/` 를 서빙한다.
- 근거: 빌드 단계가 없어 `npm start` 즉시 실행이 가능하고 실패 지점이 줄어든다. 목업이 픽셀 단위로 구체적이라 직접 CSS 를 쓰는 편이 대조가 쉽다.
- 영향: CSP 에 `app:` 스킴을 포함해야 한다.

## D-004. 유튜브 수집: provider 2중화 (yt-dlp 우선 + native 폴백)

- 배경: 실측 결과 같은 영상에 대해 native(HTML) 경로는 메타데이터·자막 트랙 목록은 얻지만 **자막 본문은 0바이트**였다(봇 차단). yt-dlp 는 같은 환경에서 자막 본문(json3) 수집에 성공했다.
- 결정: 기본은 `auto` = yt-dlp 사용 가능 시 yt-dlp, 없으면 native. 설정에서 강제 선택 가능.
- 근거: 자막이 없으면 앱의 핵심 가치(문장 학습)가 성립하지 않는다. yt-dlp 는 자막 본문 확보가 검증된 경로다.
- 영향: yt-dlp 탐지/다운로드/상태 UI 가 필수가 된다. native 만으로도 채널 등록·영상 목록·재생은 동작한다.

## D-005. API 키 저장: `safeStorage` 암호화 + 렌더러 마스킹

- 결정: OpenRouter 키는 메인에서만 다루고 DB 에는 `safeStorage.encryptString` 결과(base64)를 저장한다. 렌더러에는 `hasKey`, 마스킹 문자열, 저장 시각만 전달한다.
- 근거: AGENTS.md / SKILL.md §31 Secret 보호 규칙.
- 예외: `safeStorage.isEncryptionAvailable()` 이 false 인 환경에서는 평문 저장하고 UI 에 경고를 표시한다(로컬 전용 앱 한정 허용).

## D-006. Cloudflare 규칙 비적용

- 배경: SKILL.md §19 는 wrangler 설정·workers-types·binding 존재 시 Cloudflare 프로젝트로 판단한다.
- 결정: Phase 0 에서 해당 항목이 전혀 없음을 확인했으므로 **§20~§29 를 적용하지 않는다**. 또한 §22 의 Node.js API 금지 규칙도 적용하지 않는다(Electron 데스크톱 앱은 파일 시스템·child_process 사용이 본질적 요구사항).
- 근거: §34 의 실패 기준 중 "Cloudflare 에서 지원되는지 확인하지 않고 런타임 API 사용"은 Cloudflare 프로젝트 한정 규칙이다.

## D-007. 재생은 YouTube IFrame 임베드 사용

- 결정: 영상 다운로드 없이 YouTube IFrame Player API 로 재생한다.
- 근거: 사용자 요청은 "동영상을 듣는 것"이며 다운로드는 명시 요구가 없다. 저작권·용량·정책 리스크를 피한다.
- 영향: 듣기/자막 모드 전환은 `cc_load_policy` 를 바꿔 플레이어를 재생성하고 현재 시간을 복원하는 방식으로 구현한다. 현재 문장 하이라이트는 IFrame API 의 `getCurrentTime()` 폴링으로 동기화한다.
- 보류: 오프라인 재생은 T24/T25 와 함께 보류 항목으로 둔다.

## D-008. 데모 데이터 시딩

- 결정: 첫 실행 시 빈 상태 안내를 띄우고, 사용자가 명시적으로 요청하거나 `--demo` 플래그로 실행할 때만 UI.png 목업과 동일한 데모 데이터를 넣는다.
- 근거: 실제 데이터와 가짜 데이터를 섞지 않는다. 스모크 테스트는 `--demo` 로 UI 대조를 수행한다.

## D-009. 동영상 URL 은 provider 와 무관하게 항상 채운다

- 배경: native provider 는 채널 목록 응답에서 `videoId` 만 얻고 `url` 을 만들지 않았고, DB 의 `videos.url` 은 NOT NULL 이다.
- 결정: native provider 의 항목 생성 시점에 ` https://www.youtube.com/watch?v=<videoId> ` 를 넣고, 오케스트레이션(syncChannel)에서도 entry.url ?? watch URL 폴백을 둔다. DB 계층은 `title`/`url` 을 `?? null` 로 방어한다.
- 근거: provider 출력 스키마를 동일하게 유지해야 상위 계층이 분기 없이 동작한다. 근본 원인(provider)에서 고치고 상위는 방어만 한다.
- 영향: extractVideoEntries 출력에 url 키가 추가된다(테스트 기대값도 함께 갱신).

## D-010. 실제 수집 검증은 별도 E2E 스크립트로 분리

- 결정: 네트워크에 의존하는 실제 채널 수집 검증은 `scripts/e2e-collect.js` 로 분리하고 `npm test`(단위)·`npm run smoke`(오프라인 부팅)에는 넣지 않는다.
- 근거: 단위 테스트/스모크는 네트워크 상태와 무관하게 항상 같은 결과가 나와야 한다. E2E 는 --url=/--limit=/--native 옵션과 STUDY_TED_E2E_URL 환경변수로 대상을 바꿀 수 있게 하고, userData 를 _tmp/e2e-userdata 로 격리한다.
- 영향: 검증 절차가 4단계(문법 → 단위 → 스모크 → E2E)가 된다.

## D-011. 렌더러는 커스텀 스킴 대신 loopback HTTP 로 서빙한다

- 배경: "동영상을 재생하지 못했습니다" 가 모든 영상에서 발생했고, YouTube 플레이어는 `error 153` 을 반환했다. 네트워크·임베드 허용 설정·영상 ID 는 모두 정상이었다.
- 원인: 렌더러를 커스텀 스킴 `app://study-ted` 로 띄우면 Chromium 이 그 스킴의 요청에 `Referer` 를 붙이지 않는다. YouTube 는 임베드 요청의 출처를 Referer 로 판정하므로 재생을 거부한다. `webRequest` 로 Referer 를 강제 주입해도, `<meta name="referrer">` 로도 해결되지 않는다(스킴 단위 제약).
- 결정: 렌더러를 `http://127.0.0.1:<임의 포트>`(`listen(0, '127.0.0.1')`, 루프백 전용)에서 서빙한다. Host 헤더가 루프백이 아니면 403, 정적 자산 외 경로는 404 로 응답한다.
- 근거: 같은 렌더러를 http 로 열면 재생이 정상 동작함을 실측으로 확인했다(`duration: 1174`, 오류 0, 요청 헤더에 Referer 존재). 기능을 깎지 않으면서 원인을 제거하는 방법이었다.
- 영향: CSP 에서 `app:` 를 제거하고 `'self'`(= loopback origin)로 통일했다. 앱 종료 시 서버를 닫는다. 회귀 방지는 `npm run e2e:player` 가 담당한다.
- 트레이드오프: 로컬 포트를 하나 점유한다. 외부 노출은 없고(`127.0.0.1` 바인딩 + Host 가드) 포트는 OS 가 매번 임의로 배정한다.

## D-012. `refreshExisting` 기본값은 "켜짐", 자막은 옵션과 무관하게 건너뛴다

- 배경: 사용자 요청은 "기존 영상이 있으면 메타 갱신을 건너뛰는 옵션"이다. 옵션의 기본값에 따라 기존 사용자의 동작이 바뀐다.
- 결정: `collect.refreshExisting` 기본값은 `1`(켜짐)이고, 설정에서 끄면 `refresh=false` 로 동작한다.
- 근거: 기본을 끄면 기존 사용자가 조회수·제목 변경을 받지 못하는 조용한 동작 변경이 된다. 기본 켜짐은 3차 라운드까지의 동작과 같아 회귀가 없다. "새 데이터만 저장" 을 원하는 사용자는 한 번만 끄면 되고 그 선택은 설정에 남는다.
- 구현: 끄면 `videosDb.upsert(video, { refresh: false })` 가 `ON CONFLICT DO NOTHING` 으로 기존 행을 보존하고 신규 행만 삽입한다. 자막은 이 옵션과 무관하게 "이미 저장된 자막은 다시 받지 않는다" 를 유지한다(같은 결과를 다시 받는 낭비 방지).
- 영향: `syncChannel` 이 `addedCount`/`keptCount` 를 반환하고 진행 메시지·토스트에 `신규 N개 · 기존 K개 정보 유지` 로 표시한다.

## D-013. 재생 오류는 코드별 메시지로 분리한다

- 배경: 재생 실패를 모두 "네트워크 상태를 확인해 주세요" 로 안내해 사용자가 네트워크만 의심하게 만들었다(D-011 의 실제 원인은 스킴 문제였다).
- 결정: `player.js` 에 `describePlayerError(code)` 를 두고 2(잘못된 ID) / 5(HTML5 미지원) / 100(삭제·비공개) / 101·150(임베드 제한) / 그 외(네트워크·기타) 로 메시지를 나눈다. 데모 데이터(가짜 ID)에는 "데모 영상은 실제 YouTube ID 가 아니다" 안내를 덧붙인다.
- 근거: 사용자가 다음에 취할 행동(다른 영상 선택 / 설정 변경 / 네트워크 확인)이 코드마다 다르다. 행동이 달라지는 메시지만 가치가 있다.
- 영향: 토스트 표시 시간을 7초로 늘려 긴 문구를 읽을 수 있게 했다. `isVideoError(code)` 로 데모 안내 부착 여부를 판단한다.
## D-014. 무제한 수집은 숫자 대신 `Infinity` 센티널로 표현한다

- 배경: "채널 전체 수집" 을 표현할 값이 필요했다. `0` 이나 `-1`, `'all'` 같은 대안이 있었다.
- 결정: 설정에는 `collect.collectAll`(`'1'`/`'0'`)을 따로 두고, 렌더러·IPC 경계에서는 `'all'` 을 허용하며, 수집 모듈 내부에서는 `resolveLimit()` 가 `Infinity` 로 정규화한다.
- 근거: 상한 비교가 `Number.isFinite(limit)` 한 줄로 통일되어 두 provider 의 분기가 같아진다. `0` 을 "무제한" 으로 쓰면 `while (videos.length < 0)` 처럼 실수하기 쉽고, `-1` 은 다른 언어 관례와 충돌한다. 문자열 `'all'` 을 내부까지 끌고 가면 산술 비교마다 방어가 필요하다.
- 영향: `Infinity` 는 JSON 직렬화에서 `null` 이 된다. 그래서 IPC 반환값·진행 이벤트에는 유한할 때만 `total` 을 채우고 무제한이면 `0` 을 보낸다(렌더러는 0을 "총량 미정" 으로 해석).

## D-015. 전체 수집이 기본값이다 (개수 제한은 옵션으로 남긴다)

- 배경: `collect.limit` 기본 24 때문에 사용자가 "채널을 다 긁지 않는다" 고 판단했다. 실제로는 상한이 걸려 있었을 뿐이다.
- 결정: `collect.collectAll` 기본값을 `1`(전체 수집)로 하고, 개수 제한 입력은 전체 수집을 끈 뒤에만 활성화한다.
- 근거: 사용자의 기대는 "채널을 등록했으면 그 채널 영상이 들어온다" 이다. 24는 초기 개발 중 네트워크 부하를 줄이기 위한 임시값이었고 사용자 기대와 어긋났다. 무제한은 느릴 수 있으므로 (1) 진행률로 확인하고 (2) 언제든 취소할 수 있고 (3) 개수 제한으로 되돌릴 수 있게 했다.
- 영향: yt-dlp 타임아웃이 무제한일 때 30분으로 늘어난다. `refreshExisting` 덕분에 두 번째 수집은 기존 영상 메타를 건너뛰어 실제 비용은 "신규 영상 + 아직 없는 자막" 뿐이다.

## D-016. 자막 오버레이는 프레임을 채우는 요소가 아니다

- 배경: `.player-frame > div { width:100%; height:100% }` 는 플레이어 호스트를 채우려던 규칙이었지만 직계 `div` 인 자막 상자까지 잡았다.
- 결정: 100% 채우기 규칙은 클래스 선택자(`.player-host`, `.player-note`)로 좁히고, 자막 상자는 `height:auto` + `max-height:60%` 로 내용 크기만 차지하게 한다. 프레임 배경(`#0d131f`)은 영상 로딩 전 여백용으로 유지한다.
- 근거: 구조 선택자(`> div`)는 나중에 형제 요소가 추가되면 조용히 규칙이 번진다. 클래스 선택자는 의도가 코드에 남고, 자막은 "덮는 레이어" 가 아니라 "하단 캡션 상자" 라는 의미가 CSS 에 드러난다. `iframe`/`div` 두 선택자를 함께 두면 iframe 크기 규칙도 유지된다.
- 영향: 자막이 길어지면 60% 높이에서 내부가 잘린다(`overflow:hidden`). 프레임을 덮지 않는 것이 우선이며, 스크롤 가능한 자막은 오른쪽 패널이 담당한다.

## D-017. 수집 개수는 channels 조회 경로에서 계산한다

- 배경: 채널 행에 "몇 개 불러왔는지" 를 보여주려면 영상/자막/문장 수가 필요하다.
- 결정: 뷰에서 각각 조회하지 않고 `main/db/channels.js` 의 공용 `COLUMNS` 에 상관 서브쿼리 3개를 추가한다. `list()`·`getByPk()`·`getByChannelId()`·`touchSync()` 가 같은 컬럼을 함께 돌려준다.
- 근거: 화면마다 따로 세면 조회 시점이 달라 숫자가 어긋난다. 개수를 한 곳에서 계산하면 모든 읽기 경로가 일관되고 `main/ipc.js` 도 수정할 필요가 없다.
- 영향: 채널 수가 아주 많아질 때 목록 조회 비용이 서브쿼리 수만큼 늘어난다. 채널 목록은 수십 개 수준이고 각 서브쿼리에 인덱스(`videos.channel_pk`, `sentences.channel_pk`)가 걸려 있어 문제되지 않는다.

## D-018. 전송 버튼과 줄 클릭을 분리한다

- 배경: 자막 줄 클릭은 이미 "그 지점부터 재생" 이라는 의미를 가지고 있었고, 여기에 전송을 얹으면 재생하려다 문장이 보내진다.
- 결정: 줄 안에 `문장 전송` 버튼을 따로 두고, 버튼 클릭은 `stopPropagation()` 으로 줄 클릭과 끊는다.
- 근거: 한 요소에 두 동작을 겹치면 사용자가 의도를 표현할 방법이 없다. 컨트롤을 분리하면 "재생" 과 "보내기" 가 각각 한 가지 의미만 가진다.
- 영향: 자막 줄은 `[시간][문장][버튼]` 3열이 된다. 버튼은 `flex:0 0 auto` 로 고정 폭이고 평소 반투명(`opacity:0.55`)이라 문장 읽기를 방해하지 않는다.

## D-019. 줄 클릭은 이동 후 재생까지 한다

- 배경: 사용자가 자막 줄을 눌렀을 때 기대하는 것은 "그 부분을 다시 듣기" 다.
- 결정: `replayFrom(seconds)` 가 `player.seekTo(seconds)` 와 `player.play()` 를 함께 호출한다.
- 근거: `seekTo` 만 호출하면 위치만 옮겨지고 일시정지 상태가 유지되어 "눌러도 아무 일이 없는" 것처럼 보인다.
- 영향: 재생 중에 줄을 눌러도 재생이 끊기지 않고 새 위치에서 이어진다. 자막 하이라이트는 기존 폴링 로직이 새 재생 위치를 따라간다.

## D-020. 가격은 메인에서 한 번만 파생하고, "가격 미정" 과 "무료" 를 구분한다

- 배경: 모델 목록에 가격을 보여주고 가성비 순으로 추천하려면 단가를 숫자로 다뤄야 한다. OpenRouter 원본은 `USD / 1 token` 이라 그대로 보여주면 읽기 어렵고, 비교하려면 환산이 필요하다.
- 결정: 환산(`pricePerMillion`)·표기(`priceLabel`/`priceShort`)·점수(`priceScore`)·정렬(`rankModels`)·검색(`filterModels`)을 전부 `main/ai/openrouter.js` 에 두고, `decorateModels(raw)` 결과를 기존 `ai:models` 응답에 실어 보낸다. IPC 채널·응답 모양은 그대로 두고 필드만 늘린다.
- 근거: 같은 숫자를 렌더러와 메인이 각각 계산하면 표기와 순위가 어긋난다. 값이 하나뿐이면 "왜 3위인데 더 비싸 보이지" 같은 불일치가 생길 수 없다. IPC 를 늘리면 preload·api·actions·뷰까지 배선이 따라 늘어나므로 기존 응답을 재사용했다.
- 영향: 단가 `0` 은 `무료`, 음수 단가(`-1`, 라우팅 모델)는 `가격 정보 없음`/`가격 미정` 으로 **다르게** 표기한다. 미정을 0원으로 취급하면 가성비 1위로 올라와 추천이 망가진다. 점수는 입력 40% · 출력 60% 가중 평균으로 두어, 대화형 사용에서 비중이 큰 출력 단가를 더 반영한다.
- 영향: 렌더러는 목록 서명(`listSignature`)이 바뀔 때만 다시 그린다. 검색은 표시용 이름과 ID 를 모두 대상으로 하고 결과를 200개로 끊어 좁은 화면에서도 렌더 비용이 일정하다.

## D-021. 취소는 한 곳에서 관리하고, signal 을 자식 프로세스까지 전달한다

- 배경: 2000개 이상 자막을 받는 중에 정지할 방법이 없었다. 취소 배선 자체는 있었지만 `assertNotCancelled` 가 루프 경계 검사뿐이었고, 자막 1건이 yt-dlp 자식 프로세스로 최대 150초를 잡고 있었다. 정지가 "2분 뒤에 먹는" 상태였다.
- 결정: (1) 취소 플래그와 `AbortController` 를 `main/collect/job-registry.js` 한 모듈로 모으고, (2) `AbortSignal` 을 `net.fetchText`·`native-provider`·`ytdlp-manager.run` 까지 **끝까지 전달**한다. 취소 오류는 `code:'CANCELLED'` 하나로 통일하고 재시도하지 않는다.
- 근거: 이전 구조는 취소 경로가 모듈마다 흩어져 있어 "지원하는데 아무도 안 쓰는" dead code 가 생겼다(`ytdlp-manager.run` 의 signal 인자). 상태를 한 곳에 모으면 새 provider·새 네트워크 호출을 추가할 때 배선 누락을 찾기 쉽다. 루프 경계 검사만으로는 단위 작업이 길어질 때 반응이 늦어지므로, 중단은 자식 프로세스와 소켓 수준에서 일어나야 한다.
- 영향: 취소 직후에도 실행 시간이 남아 있는 작업이 없다(취소 E2E 실측 `elapsedMs:30012`, 요청 후 12ms). 재시도를 막아 "취소했는데 다시 붙는" 동작을 없앴다.
- 영향(부분 결과 보존): 취소 시점까지 저장된 영상·자막·문장은 삭제하지 않는다. 이미 쓴 네트워크 비용과 사용자 시간을 버리지 않는 편이 낫고, 정지는 "되돌리기" 가 아니라 "그만 받기" 다. 반환값과 `error.detail` 에 `cancelled:true` 와 partial 값을 함께 실어 화면이 "실패" 와 "정지" 를 구분할 수 있게 했다.

## D-022. 자막 수집은 배치가 아니라 동시성으로 처리한다

- 배경: 자막을 영상 1편씩 순차로 받으면 편당 9~11초가 걸려 2000편이면 5~6시간이다. 먼저 `--batch-file` 로 프로세스 하나에 여러 영상을 넘기는 방법을 재봤지만 1.37x 밖에 줄지 않았다. 병목은 프로세스 생성 비용이 아니라 편당 네트워크 왕복 대기였다.
- 결정: 자막 단계를 `collectSubtitles()` 워커 풀로 바꿔 N개 영상의 `yt-dlp` 프로세스를 동시에 띄운다. 동시 개수는 설정 `collect.concurrency`(기본 4, 허용 1~8). `--batch-file` 은 채택하지 않는다.
- 근거: 실측(TED 6편) 순차 55,628ms(편당 9,271ms) vs 동시 4 24,307ms(편당 4,051ms) = **2.29x**. `--batch-file` 은 1.37x 였고, 게다가 편당 타임아웃이 사라지고 한 편이 멈추면 배치 전체가 멈추며 진행률을 파일 diff 로만 알 수 있어 8차의 "정지가 즉시 먹는다" 계약이 깨진다.
- 영향: 편당 개별 타임아웃·진행률(`subtitle i/n · 남은 K개`)·정지 즉시성이 유지된다. 워커는 같은 `AbortSignal` 을 공유해 정지 시 진행 중 프로세스가 동시에 죽고, 대기 중 워커는 루프 선두의 `assertNotCancelled` 로 새 작업을 시작하지 않는다. 임시 폴더는 `tmp/collect-<jobId>/<videoId>` 로 편 단위 분리해 동시 실행에서 서로의 파일을 지우지 않는다.

## D-023. 진단용 `수집 환경` 카드는 기본 숨김, 수집 불가일 때만 표시

- 배경: 채널 관리 상단 `수집 환경` 카드는 provider·yt-dlp 경로 같은 내부 정보를 노출해 일반 사용자에게는 노이즈다.
- 결정: 기본 상태를 `hidden` 으로 두고, `settings.preference === 'ytdlp' && !ytdlp.available` — yt-dlp 를 쓰기로 했는데 yt-dlp 가 없어 수집이 **불가능한** 경우에만 자동으로 보여 내려받기를 유도한다.
- 근거: 카드를 그냥 지우면 수집 실패 원인을 안내할 곳이 사라진다. 같은 정보와 `yt-dlp 내려받기` 는 이미 설정 화면에 있으므로 정상 상태에서 카드가 없어도 기능 손실이 없다.
- 영향: 노출 여부는 `refreshStatus()` 끝에서 한 곳에서만 정한다(`statusCard.hidden = !(status.preference==='ytdlp' && !ytdlp.available)`). 스모크 `view:channels` 가 기본 숨김을 확인한다.

## D-024. 자막은 영어 트랙만 받고, 받는 파일 수와 `kind` 를 줄인다

- 배경: 기존 `--sub-langs en.*,en` 은 정규식이라 `en-fr`·`en-hu` 같은 자동 번역 트랙까지 함께 받아 편당 2~3개 파일이 생겼고, 받은 트랙을 `kind:'asr'` 로 기록해 실제 자동생성 자막이 아닌 트랙까지 ASR 로 표시됐다.
- 결정: `LANG_ATTEMPTS = ['en', 'en.*,en']` 로 **영어 1개**를 먼저 시도하고, 파일이 하나도 안 생기면(영어 트랙 없음) 넓은 패턴으로 **1회만** 재시도한다. 저장되는 `kind` 는 `'asr'` 대신 `null` 로 둔다.
- 근거: 실측에서 `en` 지정 시 4/4 영상이 정확히 1개 파일을 받았다. 목적이 영어 학습이므로 다른 언어 트랙은 저장 공간과 시간만 쓴다. `kind` 는 어떤 트랙인지 확실히 구분할 수 없을 때 단정하지 않는 편이 낫다.
- 영향: 편당 내려받기가 2~3개 → 1개로 줄어 동시 수집과 맞물려 처리량이 개선된다. 영어 트랙이 없는 영상은 넓은 패턴 재시도로 이전과 같이 처리된다.

## D-025. 문장 전송은 덮어쓰지 않고 줄 단위로 누적한다

- 배경: 자막 줄의 `문장 전송` 이 기존 입력칸을 지우고 그 문장만 넣어 여러 문장을 모아 저장할 수 없었다. 원인은 전송 경로가 "저장된 문장을 불러온다"는 의미의 `setSentence()`(교체)를 그대로 쓴 것이다.
- 결정: `SentencePanel.appendSentence(text, { focus, startSec })` 를 신설해 **줄 단위 중복 검사 후 `\n` 으로 덧붙인다**. `setSentence()` 는 저장된 문장을 다시 여는 경로 전용으로 남겨 덮어쓰기를 유지한다.
- 근거: 한 메서드가 "교체"와 "추가" 두 의미를 겸하면 호출부마다 의도가 드러나지 않는다. 분리하면 저장 문장을 여는 동작을 건드리지 않고 전송만 누적할 수 있다. 전송 시점의 재생 위치는 `startSecs: Map<문장, 시작초>` 에 문장별로 기록해 저장할 때 그 문장의 값을 쓰고, 전역 선택 시각으로 폴백하던 경로는 제거했다.
- 영향: 이미 있는 문장을 다시 보내면 줄이 늘지 않고 `이미 문장 패널에 있는 문장입니다.` 만 알린다. 스모크가 "2줄 전송 → 같은 줄 재전송 → 여전히 2줄" 을 고정한다.

## D-026. AI 구문분석은 저장을 전제로 하고 결과를 즉시 보여준다

- 배경: 기존 흐름은 `문장 저장 → 학습 자료 목록에서 다시 열기 → AI 구문분석` 이라, 저장하지 않고 AI 를 누르면 분석할 대상이 없었다.
- 결정: `actions.analyzeAndSaveSentence()` 가 `api.ai.analyze` → `api.sentences.create({ source:'ai', translation, analysis, startSec, videoPk/… })` → 목록·자료 갱신 → `{ ...result, saved }` 반환까지 한 번에 수행한다. 버튼 한 번이면 분석 + 저장 + 표시가 끝난다.
- 근거: 사용자가 원하는 결과는 "이 문장을 이해하는 것"이고 그 결과는 남아 있어야 다시 볼 수 있다. 분석 결과(쉬운 설명·문법 포인트·예문)와 해석을 함께 저장하면 목록에서 다시 열었을 때 같은 내용이 보인다.
- 영향: 저장된 문장은 입력칸에서 사라지고 분석 결과는 패널에 남는다. 한 번에 최대 `MAX_ANALYZE_LINES = 5` 문장을 처리하고 초과분은 입력칸에 남기며, 진행 중 버튼은 `분석 중… i/n` 을 표시한다. 기존 `analyzeSentence`(저장 문장 단위 분석)와 `sentences.create` 계약, IPC·스키마는 변경이 없다.

## D-027. 동영상 목록은 배열 계약을 유지하고 총계·hasMore 는 별도 IPC 로 준다

- 배경: 동영상이 2000편을 넘으면 목록을 한 번에 넘길 수 없다. 그렇다고 `videos.list` 의 반환을 객체로 바꾸면 기존 호출부·테스트가 모두 깨진다.
- 결정: `videosDb.list` 는 **배열**을 그대로 돌려주고 `q`/`offset` 만 받는다. 총계와 다음 페이지 여부가 필요한 화면은 새 `videos:page` 를 써서 `{ items, total, offset, limit, hasMore }` 를 받는다. 목록과 개수는 `buildFilter()` 라는 **한 곳**에서 같은 조건을 만든다.
- 근거: 기존 계약을 지키면 회귀 위험이 없고, 페이지 화면만 새 계약을 쓴다. `total` 을 목록과 분리하면 `N개 중 i–j` 표시를 위해 전체를 세는 비용도 필요한 시점에만 낸다.
- 영향: `videos:list` 는 남아 있고 스모크도 그대로 통과한다(`limit:200` 호출도 동작). 페이지 크기는 렌더러 상수 `VIDEO_PAGE_SIZE = 50`.

## D-028. 검색은 채널 드롭다운을 대체하지 않고 그 아래에 두며, 필터링은 메인에서 한다

- 배경: 사용자는 화면의 "TED-Ed · 2.2K videos" 자리에 검색을 넣자고 했다. 그러나 그 문자열은 채널 **선택** 드롭다운의 옵션 텍스트다. 지우면 채널 전환이 불가능해진다.
- 결정: 드롭다운을 유지하고 **바로 아래**에 검색 입력을 둔다. 검색은 렌더러가 아니라 SQLite(`LIKE`, `ESCAPE '\'`)에서 수행하고 결과 페이지만 렌더러로 넘긴다.
- 근거: 2000편을 렌더러로 넘겨 거르면 IPC 페이로드와 메모리가 그대로 커져 "부하가 걸리지 않게" 라는 요구를 만족하지 못한다. 검색어는 260ms 디바운스로 한 번만 조회하고, 빠른 타이핑에서 늦게 온 응답은 토큰으로 버린다.
- 영향: 검색어를 바꾸면 항상 첫 페이지(offset 0)로 돌아간다. 와일드카드(`%`, `_`)는 문자로 취급한다. 채널을 바꾸면 검색어를 비운다.

## D-029. AI 분석은 재시도로 살리고, 저장된 분석은 문장 노트에 그대로 보여 준다

- 배경: 사용자가 "AI 구문분석을 누르면 문장이 자동저장되어야 하고, 해석·구문분석이 문장 노트에 저장되어야 하는데 저장이 안 된다"고 보고했다. 실측 결과 로그에 429(`요청이 너무 많습니다`)가 14회 연속 찍혀 있었고 실사용 DB 의 저장 문장 2건은 모두 `analysis_json` NULL 이었다.
- 결정 1(재시도): `request()` 에 지수 백오프 재시도를 넣고 재시도 대상은 **일시 오류만**(408·429·500·502·503·504·네트워크)으로 한정한다. `Retry-After` 헤더가 있으면 지수 계산보다 우선한다. 두 번 모두 실패하면 `AI_RATE_LIMIT` 으로 "다른 모델을 선택해 주세요(무료 모델은 사용량 제한이 잦습니다)"를 안내한다.
- 결정 2(노출): `renderer/js/components/analysis-card.js` 로 분석 카드를 공용화하고, 문장 노트 표에 `분석` 컬럼(요약 + `분석 보기` → 숨겨진 `tr.is-detail` 펼침)을, 학습 자료 목록에 요약 pill + `분석` 토글을 넣는다.
- 결정 3(실패 표시): 분석이 실패하면 직전 성공 결과를 지우고 `.analysis--error` `분석하지 못한 문장` 카드로 실패 문장과 이유를 보여 준다.
- 근거: 저장 계층은 왕복 검증(`_tmp/analysis-roundtrip.js`)에서 정상이었으므로 손대지 않았다. 401·400 같은 영구 오류를 재시도하면 사용자는 이유 없이 기다리기만 한다. 표(`<table>`)는 `<div>` 를 직계 자식으로 가질 수 없어 상세를 **숨겨진 행**으로 두고 토글한다. 분석 박스가 하나뿐인데 실패 시 직전 결과를 남기면 사용자는 저장된 것으로 오해한다 — "안 보이면 저장 안 된 것"과 같은 문제다.
- 영향: 무료 모델을 계속 쓰더라도 일시적 429 는 대개 흡수된다. 저장된 분석은 어떤 모델이 만들었는지(`analysis.model`)까지 노트에 남는다. 소급 복구는 불가능하므로 이미 NULL 로 저장된 문장은 다시 분석해야 한다(README 문제 해결 표에 안내).

## D-030. 영어로 나와야 하는 필드는 프롬프트로 강제하고, 응답을 검증해 1회 교정한다

- 배경: "AI 구문분석을 한 번 하면 정상적으로 영어 + 한국어 설명이 나오는데, 갑자기 전부 한국어로 보인다"는 신고가 있었다. 화면(렌더러)을 의심했지만 실사용 DB 를 열어 보니 **같은 화면에 정상 분석과 오염 분석이 함께** 있었고, 오염은 `structure[].part`(영어 구문)까지 한국어로 채워진 **모델 출력** 문제였다. 사용 모델은 무료 8B(`meta-llama/llama-3.1-8b-instruct`)였다.
- 결정: `systemPrompt`/`userPrompt` 에 "`part` 는 문장에서 그대로 복사한 영어, 한글 금지 / 한국어는 `translation`·`meaning`·`note` 에만" 규칙을 명시하고, 응답을 받은 뒤 `findLanguageMismatch()` 로 `structure[].part` 만 검사해 오염이 있으면 **교정 프롬프트로 1회만** 재요청한다. 교정본의 오염 개수가 줄어들 때만 채택하고, 그래도 남으면 카드 상단 `.analysis__warn` 노란 경고로 사실을 알린다.
- 근거: 검사 대상을 `part` 하나로 좁힌 이유는 나머지 필드의 한국어가 **정상**이기 때문이다. 무한 재시도를 피한 이유는 소형 모델이 반복해도 같은 실수를 할 수 있고, 실패하면 사용자가 이유 없이 기다리기 때문이다.
- 영향: 8B 무료 모델에서도 대부분 교정된다. 교정이 실패하면 화면이 오염 사실과 다음 행동(설정에서 더 큰 모델 선택)을 안내한다. 이미 저장된 오염 분석은 소급 복구되지 않으므로 다시 분석해야 한다(README 문제 해결 표에 안내).

## D-031. 분석 카드는 문장 해석·구문 분석 두 항목만 두고, 표현·예문·원문 응답은 화면에서 뺀다

- 배경: 사용자가 "분석보기를 눌러도 영어 구문에 대한 설명은 안 보이고 한국어만 보인다", "하단에 나오는 AI 원문 응답은 없어도 된다", "문장 해석·구문 분석만 해줘. 주요표현·예문 필요없어 보여"라고 연속해 요청했다.

## D-032. 메모·태그는 화면에서 숨기지 않고 DB 컬럼·테이블을 실제로 삭제한다

- 배경: 사용자가 "문장 노트저장할 때도 주요표현, 예문, 메모, 태그도 필요없어… 디비에서 빼줘도 돼… 수동수정할때도 마찬가지로 반영하게 해줘"라고 요청했다.
- 결정: `main/db/schema.js` 에 두 번째 마이그레이션 `dropSentenceNoteAndTags` 를 추가해 `DROP TABLE IF EXISTS sentence_tags;` → `DROP TABLE IF EXISTS tags;` → `ALTER TABLE sentences DROP COLUMN note;` 를 한 번에 실행한다(`schema_version` 1 → 2). **`initial` 마이그레이션의 CREATE 문은 그대로 둔다**(그 버전으로 만들어진 DB 이력을 그대로 재현해야 신규 설치와 기존 설치가 같은 경로를 지난다).
- 근거: 입력칸만 숨기면 값은 DB 에 계속 쌓이고, 나중에 되살릴 때 지저분한 데이터가 그대로 나온다. 사용자가 저장한 것은 문장·해석·분석(`analysis_json`)이므로 그 세 가지만 보존하면 된다.
- 영향: 화면(표 컬럼·수정 모달·수동 입력) → IPC(`sentences:list` 의 `tag`, `sentences:create/update` 의 `note`·`tags`, `tags:list`) → preload/렌더러 `api.tags` → DB 쿼리(`setTags`·`listTags`·태그 조인) → 공유 내보내기·가져오기 → 데모 시드 → 테스트·스모크까지 함께 제거해 죽은 경로를 남기지 않았다. **주의**: `analysis.structure[].note` 는 구문 설명(예: "want to + 동사원형")으로 요청 대상이 아니므로 그대로 유지한다. 실사용 DB 사본 검증에서 영상 2,358 · 자막 144 · 문장 4 행 수가 모두 보존됐다. 살아 있는 DB 는 앱 재시작 시 자동으로 마이그레이션된다.

## D-033. 구문 항목은 한국어 뜻을 반드시 갖고, 문장을 단어로 쪼개지 않는다

- 영향: 같은 문장이 8B 에서도 4개 의미 덩어리 + 한국어 뜻으로 나온다. 이미 저장된 단어 분할·뜻 없음 분석은 소급 복구되지 않으므로 문장 노트의 `AI 다시 분석` 버튼(`reanalyzeSentence`)으로 갱신해야 한다(버튼은 문제가 있는 문장에만 나타난다).
## D-034. 배포는 electron-builder NSIS 설치본, 업데이트는 사용자가 지정한 JSON 피드로 받는다

- 배경: 사용자가 "버전 업그레이드 되면 자동으로 다운로드 받을 수 있도록 홈상단에 버전표시 해주고, 업데이트 있으면 있다고 표기하고 누르면 다운로드 되서 업데이트 되도록" 요청했다. T24(배포 패키징)는 1차 라운드부터 `HOLD` 로 남아 있었다.
- 결정 1(패키징): `electron-builder` 의 **NSIS 설치본**(`StudyTED-Setup-<version>.exe`, x64, per-user)을 만들고, 아이콘은 외부 도구 없이 생성하며(`scripts/make-icon.js`), yt-dlp 는 `extraResources` 로 `resources/bin` 에 실어 나른다. `deleteAppDataOnUninstall: false` 로 두어 **업데이트해도 학습 데이터(`%APPDATA%\study-ted`)가 보존**되게 한다.
- 결정 2(업데이트): `autoUpdater`(Squirrel) 대신 **사용자가 설정에 넣은 JSON 피드**를 직접 읽는 방식을 쓴다. 피드는 `{ version, url, sha256, size, notes, pubDate }` 이고 `url` 은 상대 경로도 허용한다.
- 결정 3(통신 위치): 확인·다운로드는 **메인 프로세스**에서만 한다. 렌더러는 loopback HTTP + CSP(`connect-src 'self' youtube`) 라 외부 요청이 불가능하고, CSP 를 풀면 보안이 약해진다. 렌더러에는 `update:status` 이벤트로 상태만 보낸다.
- 결정 4(무결성): 받은 설치 파일은 반드시 `sha256` 을 검증하고 `.part` 스트리밍을 쓴다. 불일치면 파일을 지우고 `UPDATE_HASH` 로 실패시킨다(부분 파일이 설치로 이어지는 경로를 만들지 않는다).
- 결정 5(설치): 설치본은 `apply-update.cmd` 를 만들어 `/S /D=<설치폴더>` 조용한 설치 후 앱을 다시 띄우고 자신을 지운다. NSIS 의 `/D=` 는 **줄 끝까지가 경로**이므로 다른 명령을 같은 줄에 붙이지 않는다(테스트로 고정).
- 결정 6(자동 확인 조건): 피드 주소가 없거나 `http`/`https` 가 아니면 **자동 확인을 아예 하지 않는다**. 자체 업데이트 서버를 내장하지 않으므로 주소 미설정은 정상 상태이고, 이때 요청을 보내면 오류 로그만 쌓인다. 확인 주기는 6시간(`update.lastCheckAt`) + 앱 시작 8초 후 1회.
- 결정 7(상태 초기화): 피드 주소를 지우거나 바꾸면 이전 버전 기준으로 계산된 `latest`·진행률을 `clearLatest()` 로 폐기하고 `idle` 로 되돌린다(다운로드·설치 중에는 유지). 주소가 바뀌었는데 이전 버전이 "받을 수 있음"으로 남아 있으면 사용자를 잘못 인도한다.
- 결정 8(검증 방식): 피드·다운로드 로직은 `electron` 모듈을 `require.cache` 스텁으로 대체하고 로컬 `http.createServer` 로 서빙해 단위 테스트한다(11건). 실제 네트워크에 의존하면 CI·오프라인에서 흔들린다.
- 근거: 배포·업데이트는 개발자 서버 없이도 동작해야 한다. 정적 호스팅에 exe 와 `latest.json` 을 올리는 것만으로 사용자에게 업데이트가 도달하고, 렌더러 CSP 는 그대로 유지된다.
- 영향: `package.json` 에 `version` 을 올리고 `npm run dist` 를 다시 돌린 뒤 산출물 2개를 같은 위치에 올리면 기존 설치본이 스스로 새 버전을 찾아 설치한다. **주의**: 코드 사이닝을 하지 않으므로 Windows SmartScreen 경고가 뜰 수 있고, 이미 설치된 앱이 실행 중이면 `dist` 산출물이 잠겨 빌드가 실패할 수 있다(프로세스 확인 후 재빌드).

## D-035. 배포는 GitHub 공개 저장소의 릴리스 자산으로 하고, 앱에 기본 업데이트 주소를 내장한다

- 배경: 사용자가 "니가 git 올려서 자동다운로드 하도록 해야지.. 내가 올려?" 라고 요청했다. 16차(D-034)는 **업데이트 피드를 올릴 서버를 사용자가 준비해야 한다**는 한계를 남겼고, `update.feedUrl` 기본값이 빈 문자열이라 설치 직후에는 배너가 안내 문구만 보여 주는 상태였다.
- 결정 1(배포 위치): 별도 업데이트 서버를 만들지 않고 **GitHub Releases 를 배포 서버로** 쓴다. 릴리스 자산 경로 `releases/latest/download/<파일명>` 은 항상 "최신 릴리스"를 가리키므로 피드 주소 하나(`…/releases/latest/download/latest.json`)로 버전 확인과 다운로드가 모두 해결된다.
- 결정 2(저장소 공개): 저장소를 **public** 으로 만들었다. 앱은 인증 없이 `https` 로 피드를 읽으므로 비공개 저장소면 404 가 되어 자동 업데이트가 동작하지 않는다. 커밋에서 `.env`·`node_modules/`·`dist/`·`_tmp/`·`build/bin/` 을 제외해 키와 122.9MB 설치본은 저장소에 들어가지 않는다(`.gitignore` 에 `.env`·`.env.*` 를 추가했다).
- 결정 3(기본 주소 내장): `main/db/settings.js` 의 `DEFAULTS['update.feedUrl']` 을 `https://github.com/pang980/study-ted/releases/latest/download/latest.json` 로 둔다. 사용자가 설정에서 다른 주소를 넣으면 그 값이 DB 에 저장돼 우선한다(기본값은 DB 행이 없을 때만 쓰인다). D-034 의 "주소가 없으면 자동 확인을 하지 않는다"는 규칙은 그대로 두되, 이제 기본값이 있으므로 신규 설치에서도 확인이 동작한다.
- 결정 4(배포 자동화): `scripts/release.js`(`npm run release`)가 빌드와 업로드를 한 번에 처리한다. 같은 태그가 있으면 `--clobber` 로 자산만 교체하고 릴리스 설명은 `--notes-file` 로 갱신한다. 버전 올리기(`npm version 1.0.1 --no-git-tag-version`)와 설명 작성만 사람이 하고 나머지는 한 명령으로 끝난다.
- 결정 5(자산 URL 은 상대 경로 유지): `latest.json` 의 `url` 은 계속 파일명만 쓴다. 앱이 `new URL(value, feedUrl)` 로 절대 주소를 만들기 때문에 `releases/latest/download/` 아래에서도 같은 폴더의 설치본을 정확히 가리킨다(실제 응답 200 으로 확인). 절대 주소를 박으면 저장소 이름을 바꾸거나 미러를 쓸 때 피드까지 고쳐야 한다.
- 결정 6(프로세스 실행 규칙): `gh`·`git` 은 `shell:false` 로 실행해 Node 가 인자 인용을 처리하게 하고(`--title StudyTED v1.0.0` 처럼 공백이 있는 인자가 쪼개지지 않는다), `npm` 은 `.cmd` 라서 `shell:true` 로 실행한다.
- 근거: 배포·업데이트에 개발자 서버가 필요 없어야 유지비가 0 이고, 사용자가 "설치만 하면" 업데이트를 받는다. 릴리스 자산은 GitHub 가 HTTPS·CDN·체크섬(`digest`)을 제공하므로 무결성 확인도 이중으로 된다(앱의 `sha256` 검증 + GitHub 자산 digest 일치 확인).
- 영향: 새 버전 배포는 `npm version` → (필요 시 `build/release-notes.md`) → `npm run release` 세 단계다. 설치된 앱은 시작 8초 후·6시간마다 피드를 읽어 홈 배너에 새 버전을 표시하고, 버튼 한 번으로 내려받아 조용히 설치한 뒤 다시 시작한다. **주의**: 저장소를 비공개로 전환하면 인증 없는 피드 조회가 실패해 자동 업데이트가 멈춘다(직접 호스팅 주소를 설정에 넣어야 한다).

## D-036. 분석 대상은 프롬프트 **마지막 줄**의 문장 하나로 고정하고, 확인 창은 `settled` 로 한 번만 확정한다

- 배경: 사용자가 "AI 분석할 때 선택된 문장을 해석해야 하는데 지금 동영상 제목을 해석하고 있어", "문장노트에 문장을 클릭하면 내용을 바로 볼 수 있도록", "삭제 버튼을 눌러도 지금은 삭제가 안 돼", "분석보기를 누르면 내용이 하단에 쭉 다 보일 수 있도록" 을 한 번에 요청했다(D-036 은 T53~T56 을 묶은 결정).
- 결정 1(프롬프트 순서): 분석 대상 문장을 `Sentence: …` 한 줄로 **메시지 맨 끝**에 둔다. 제목·문맥은 `Reference only (never translate or analyze these):` 블록으로 묶어 그 위에 놓고, 시스템 프롬프트에도 "분석 대상은 `Sentence:` 한 줄뿐" 이라는 규칙을 넣는다. IPC·렌더러 전달 경로는 손대지 않았다(원인이 아니었다).
- 결정 2(상세 행은 항상): 문장 노트의 상세 행을 "분석이 저장된 행에만" 만들던 것을 **모든 행에** 만들고, 분석이 없으면 그 자리에 "저장된 AI 분석이 없습니다. …" 안내를 보여 준다. 문장 셀과 `분석 보기` 버튼이 같은 `toggleDetail()` 을 쓴다.
- 결정 3(닫기가 확정을 이기지 못하게): `confirmDialog()` 는 `settled` 플래그와 `done(value)` 를 두고 확인·취소·`onClose` 가 모두 `done()` 을 거치게 한다. `close()` 안에서 `onClose` 가 동기 실행되므로 `resolve` 를 먼저 확정해야 한다. 같은 실수를 막으려고 내보내기 다이얼로그도 `resolve` → `close()` 순서로 바꿨다.
- 결정 4(높이 제한): 표 높이 제한은 `.table-wrap.is-expanded { max-height: none; }` 한 규칙으로 풀고, 상세가 하나라도 열려 있을 때만 켠다. `renderRows()` 는 다시 그리기 전에 클래스를 지워 원래 높이로 돌린다.
- 근거: 순서·확정·표시 문제는 모두 **한 곳에서 잘못 정한 규칙**이 화면 곳곳에서 다른 증상으로 나타난 사례다. 프롬프트는 대상 텍스트를 마지막에 두는 것만으로 약한 모델도 지시를 지켰고, 모달은 확정값을 한 번만 남기는 것으로 삭제·내보내기가 함께 고쳐졌다. 검증(스모크)도 "상세 행 개수 = 행 개수, 카드·버튼·요약 개수 일치" 로 바꿔 새 동작을 고정했다.
- 영향: 새 문장을 저장하면 분석이 없어도 문장을 눌러 원문·해석을 볼 수 있다. `AI 다시 분석` 버튼은 그대로라 기존 오염 데이터(`id=4`, `id=5`)는 사용자가 한 번 누르면 교정된다. 앞으로 모달을 추가할 때도 "먼저 열고 나중에 확정" 패턴을 쓰지 않는다.

## D-037. 모달은 배경 클릭으로 닫지 않고, 저장된 분석은 해석·구문 분석만 보여 준다

- 배경: 사용자가 "수정할 때 창을 벗어나면 창이 사라진다", "문장노트의 `AI 다시 분석` 버튼은 빼 달라", "`분석 보기` 에서 저장된 AI 문서와 아래 경고 문구는 없애고 바로 문장 해석·구문 분석만 보이게 해 달라" 를 요청했다(T57~T59).
- 결정 1(닫기 경로 축소): 모달은 ✕·취소·Esc 로만 닫는다. 배경 클릭 핸들러를 없앴고, Esc 는 `document` `keydown` 으로 받되 `close()` 에서 리스너를 해제한다.
- 결정 2(안내 대신 표시 규칙): 오염된 저장값을 화면에서 경고(`.analysis__warn`)로 알리던 방식을 없앴다. 대신 카드가 지켜야 할 표시 규칙(`structure[].part` 는 영어, `meaning` 은 한국어)을 프롬프트·테스트로 고정한다.
- 결정 3(카드 제목 줄은 옵션): `renderAnalysisCard(… , { head })` 옵션으로 목록 상세에서만 제목 줄(`저장된 AI 분석` + 모델명)을 뺀다. 학습 화면(문장 패널)은 제목 줄을 유지한다.
- 결정 4(중복 줄 제거): 목록 상세의 `.detail-translation` 은 카드의 `1. 문장 해석` 과 같은 값이라 뺐다.
- 근거: 사용자는 "왜 이 데이터가 이상한지" 설명보다 **바로 쓸 수 있는 화면**을 원한다. 반대로 조용히 감추면 문제를 알 수 없으므로, 화면은 결과만 보여 주고 품질 규칙은 생성 단계(프롬프트)와 검증 단계(스모크 단언)에서 강제한다.
- 영향: `AI 다시 분석` 버튼이 없어졌으므로 기존 오염 데이터는 문장 노트의 `수정` 에서 직접 고치거나 학습 화면에서 다시 분석해 저장한다. 새 분석은 프롬프트 순서(D-036) 때문에 대상 문장을 정확히 해석한다.

## D-038. 릴리스는 `npm run release` 한 번으로 빌드·태그·자산·피드까지 끝내고, 태그 이후에 커밋을 푸시한다

- 배경: 19차 UI 수정(T57~T59)을 사용자가 받을 수 있게 배포해야 했다. 사용자가 앱을 종료해 `dist\win-unpacked` 잠금이 풀린 것을 확인하고 진행했다.
- 결정 1(순서): 릴리스 노트 교체 → `npm version 1.0.1 --no-git-tag-version` → `npm run release` → `git commit/push` 순서로 고정한다. 태그·자산은 빌드 산출물에서 만들어지므로 **커밋 푸시는 배포 성공 뒤에** 한다.
- 결정 2(스크립트 재사용): `scripts/release.js` 가 로그인·origin 확인 → `npm run dist`(prepare-bin + electron-builder + make-manifest) → `latest.json` 버전·자산 3종 검사 → 태그 유무에 따라 `gh release create`/`upload --clobber` 를 스스로 판단하게 그대로 둔다. 새 태그 `v1.0.1` 은 없어서 `create` 경로를 탔다.
- 결정 3(피드는 `latest`): 앱에 내장한 기본 업데이트 주소는 태그 고정 주소가 아니라 `releases/latest/download/latest.json` 이다. 그래야 다음 릴리스에서도 사용자가 설정을 바꾸지 않아도 자동 확인이 동작한다(실측으로 `1.0.1` 확인).
- 근거: 배포 단계를 손으로 나누면 "빌드는 했는데 자산을 안 올림", "태그만 있고 자산이 없음" 같은 어긋남이 생긴다. 스크립트가 산출물·자산·피드를 한 번에 검사하고, 배포 뒤 커밋을 남기는 순서가 저장소 이력과 실제 배포 상태를 일치시킨다.
- 영향: 앞으로 버전을 올릴 때도 `build/release-notes.md` 만 고치고 `npm version` → `npm run release` → `git push` 세 단계면 된다. 사용자는 홈 상단 배지에서 업데이트 확인 후 바로 설치할 수 있다.
